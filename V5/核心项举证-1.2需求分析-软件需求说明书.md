## 2 任务概述

### 2.1 目标

**总目标：AI 承接全流程执行，人类只握关键决策**——"AI 干活、人拍板"，人从"执行者"变为"决策者"。

三大痛点 → 根因评估 → 确认的本质需求（对应行为标准①"分析、评估及确认"）：

| 表层诉求 | 根因评估 | 确认的本质需求 |
|---|---|---|
| "想用 AI 提效"（同事各自用 Copilot/ChatGPT 补全） | 收益碎片化的根因是 AI 停留在"个人补全"，未进入流程 | 需要**流程级**的 AI 承接，而非工具级辅助 |
| "人手不够"（需求持续积压） | 加人加班到顶，产能天花板在"人串行执行" | 需要 AI **角色化分工**承接全流程，放大产能 |
| "质量不稳"（文档失修、人肉审查、重复踩坑） | 根因是规范依赖人的自觉执行 | 需要**机器可执行**的规范与审查体系 |

### 2.2 用户的特点

- 使用者是公司 IT 开发团队的开发/测试/运维人员，熟悉 Java/Vue 技术栈，无 AI 平台运维经验——要求接入成本以"天"计、操作以"一句话触发"为限；
- 人在流程中的角色收敛为两个决策动作（审设计+执行 DDL、审 MR），不要求改变既有 GitLab 使用习惯。

### 2.3 假定和约束

- 全部组件须开源自托管，数据不出公司（信息安全合规约束）；
- 公司技术栈为传统 Java/Vue 单体（Oracle/Nacos/Redis/Kafka），不引入重平台改造；
- IT 无专职平台团队，自研工作量必须压缩到"编排+治理+技能"薄层；
- 高危操作（写库 SQL、权限资源 SQL、密钥）必须保留人工通道，AI 永不代执行。

## 3 需求规定

### 3.1 对功能的规定（任务分解与协同开发计划，对应行为标准①）

**体系架构规划（五层）**：Multica 平台层（自托管工作区底座）→ 编排层（Mika 调度 + 3 autopilot 巡检）→ 角色 agent 层（7 角色流水线）→ 技能层（3 系技能库）→ 目标仓库治理层（三文档红线 + 字典 + 硬约束）。

**建设任务分解为"6 脚手架 + 8 技能 + 1 治理层"（实物清单）**：

| 类别 | 清单（实物） |
|---|---|
| 建设脚手架 ×6 | aicoding-workspace-setup（一键安装主入口）/ skills-bootstrap（技能导入）/ agent-bootstrap（7 角色批量创建）/ project-init（项目绑定）/ orchestration-bootstrap（编排铺设）/ harness-bootstrap（仓库治理铺设） |
| 业务技能 ×8 | lookup-ui-reference v2/v3（UI 选型速查）/ config-auth-resource v2/v3（权限资源 SQL）/ db-schema-export（库表文档导出）/ browser-qa（浏览器 QA）/ harness-audit（结构对账）/ human-test-retro（测试复盘） |
| 治理层 | 三大治理文档 + docs/ 九子目录 + 写入拦截钩子 + Git 流 |

**协同开发计划**——各角色开工必读路由表（docs/index.md 必读顺序，实物摘录）：

| 角色 | 必读顺序 |
|---|---|
| PM | product → architecture/index → database → implicit-contracts →（+help，涉及时） |
| Tech-Lead | architecture/index → lessons 全部 |
| Developer | architecture/index（代码落位）→ standards 对应篇 → lessons/Developer |
| Tester | standards/testing → lessons/Tester |
| Reviewer | standards 全部 → lessons 全部 |
| DevOps | lessons 全部 |

### 3.2 对性能的规定

- **精度**：库表文档与数据库实况一致（工具生成唯一化）；规格与实现单态（sync-specs 回写）；
- **时间特性**：角色接力秒级（事件驱动编排信号）；小需求端到端约 5 分钟（场景演示口径）、bugfix 约 3 分钟、中大需求 30-60 分钟；
- **灵活性**：治理层可对齐模式铺设到任意仓库；多 agent CLI 可替换（opencode/Qwen/Trae 适配已验证）。

### 3.3 输入输出要求

- 输入：一句自然语言需求（chat 澄清后建 change）；人工决策门输入（G1 审四工件+执行 DDL、G2 审 MR）；
- 输出：四工件（proposal/specs/design/api）、代码与测试、review-report、test-report、MR、QA 报告、结构文档增量 MR。

### 3.4 数据管理能力要求

- 目标仓库治理结构（docs/ 九子目录字典）；疑难问题库分角色文件累积；对账基线表自动维护。

### 3.5 故障处理要求（对应行为标准②创新方案的自愈设计）

- run 失败自动断点重路由；连续失败 ≥2 次停止重试升级人工；审查打回红色退回逐条返工；连续打回 ≥2 次自动提炼教训；30 分钟兜底巡检对账全量 issue。

### 3.6 其他专门要求

安全红线：密钥仅 env 人工通道注入、永不落盘；保护路径（yml/db/sql/pom/settings）写入物理拦截；master 禁止直推只经人工 MR。

### 3.7 需求优先级与验收标准

**建设优先级划分**（与 A0 演化时间线"三步小步快跑"呼应：先地基后能力，每步验证可行再前进）：

| 优先级 | 交付物 | 划分依据 |
|---|---|---|
| **P0（地基，先行建设）** | 治理层（三大治理文档 + docs/ 字典 + 硬约束钩子）+ 6 个建区脚手架 | 无治理则 AI 产出不可信、无脚手架则无法规模化——一切能力的前提 |
| **P1（核心能力）** | 核心业务技能：UI 选型速查、权限资源 SQL 生成、库表结构导出 | 直接承接高频开发工序（选型/权限/库表文档），上线即提效 |
| **P2（增强能力）** | 浏览器 QA、结构文档对账、人工测试复盘 | 依赖 P0 治理结构与 autopilot 编排就绪后才有承载面，按需增强 |

**验收标准**：

- 系统级：§5"有效解决问题的验证"表五项（交付效能实测、两代单需求全周期、六系统规模化、接入耗时）全部达标即为系统验收通过；
- 工件级（每个 change 的可验收判据）：OpenSpec 四工件完整（proposal/specs/design/tasks，`ordering: strict` 校验通过）；单元测试全绿（`tdd_enforcement: strict`，Tests Failures = 0）；MR 经人工门 G2 合并（含文档随行，不允许事后补文档）；
- 铺设级（每个仓库接入的验收判据）：hook 自测通过（保护路径应拦截、普通路径应放行——不过不算装好）；治理占位符逐条以代码证据填充完毕。

## 4 运行环境规定（多方案比选，对应行为标准②）

**方案对比分析**：

| 方案 | 评估 | 结论 |
|---|---|---|
| A. 深化 Copilot 类补全工具 | 不改变开发模式，收益天花板低 | 放弃 |
| B. 自研多 Agent 平台 | 开发量以年计，IT 无专职平台团队 | 放弃 |
| C. **组合式：Multica + Claude Code + OpenSpec** | 复用成熟件，自研面压缩到"编排+治理+技能"薄层 | **采纳** |

### 4.1 设备

公司内网服务器（自托管 Multica：Go 后端 + PostgreSQL）+ 开发者本机 Runtime 守护进程（拉起 agent CLI）。

### 4.2 支持软件

Multica 平台、Claude Code 等 agent CLI、GitLab、目标项目构建链（Maven/JDK/Node）。

### 4.3 接口

GitLab API（repo 注册、webhook、建 MR）；数据库连接（仅导出表结构，密码 env 单次使用）；浏览器基座（gstack）。

### 4.4 控制

编排信号事件驱动为主通道，cron 巡检为兜底通道；人工门 metadata 状态机（ddl_done/role_bind）为硬前置。

## 6 分析方法实物：代码证据驱动的分析指引

需求分析不止用于立项决策，分析方法被固化为可复制的**分析指引**——治理层骨架的每项结构化占位符（16 项）都内嵌"如何从代码证据填充"的指引注释，禁止无证据编造。典型摘录（出自治理骨架模板版 `files/治理骨架模板/CLAUDE.md` 各节内嵌分析指引注释原文；QMS 仓库实铺版按仓库代码证据填充后的形态见 `files/治理文件实物/`）：

> **§5 构建工具路径——标准四步链**：① 试 PATH（mvn -v / node -v 直接跑）② 读自身进程环境变量约定 key（MVN_BIN / JAVA_HOME / NODE_BIN；agent 无权用 CLI 查 env），值只当候选——-v 验证失败即降级 ③ 探测常见安装位置（glob 模式清单跨机器通用可进 git，如 /c/Program Files/JetBrains/*/plugins/maven/lib/maven3/bin/mvn.cmd、/c/Program Files/Java/jdk*、/d/jdk*、~/.nvm/versions/*）④ 全失败停下评论人工待办（人话提示要配哪些变量，无命令），禁止瞎猜路径。每级命中先 -v 验证再正式使用。填完后在当前 runtime 按链完整走一遍实测（报告注明），保证文档写法可直接复制执行。

> **§8 分层规则**：抽样现有代码归纳（**每类 ≥3 例**）：分层链路、各层命名约定、Entity/DTO 规则、允许/禁止的用法；无分层传统的新项目则写目标分层规则并标注「新建约定」。

这类"证据链分析纪律"（≥3 例抽样、验证后使用、禁止粉饰、禁止编造）贯穿全部 16 项分析方法，是本行为要点的方法论沉淀。
