## 1 引言

### 1.1 编写目的

本报告汇总 AI 编码流水线的测试体系设计、各质量关测试结果与发现、疑难问题分类归口及问题库机制。预期读者：开发测试人员。

### 1.2 背景

- 被测系统：AI 编码体系（Harness V2 单会话阶段 → Multica 多 Agent 流水线阶段）交付的业务代码；本报告 T4 实例取自 V2 阶段（2026.06），Multica 阶段质量关配置与 V2 同源沿用（治理实物 2026.06.23 铺设后连续使用，跨两代阶段的测试样本见 T6）；承载于 LIMS / QMS 服务端 / QMS 前端 / QMS SPC / ECQ / MDM 等 Java/Vue 系统，QMS 服务端达 120+ 业务模块、279 个 Mapper.xml；
- 任务提出者：集团 IT 部；开发者：IT 开发团队（本人主导测试体系设计）；测试执行：Tester agent + Reviewer agent + 人工测试（业务人员）；
- 测试环境为内网测试库（真实库表），与生产差异主要在数据量级，对功能测试结论无实质影响。

### 1.3 定义

TDD 强制门 / 异模型只读审查门 / 浏览器 QA 三档 / 疑难问题库（错题本）/ 四源采集——定义见各章。

### 1.4 参考资料

## 3 测试结果及发现

### 3.1 测试 T1：TDD 强制门

**动态输出**：Developer 按 plan.md 单条目推进，每条目走完整红-绿-重构循环（先写测试且必须失败→最小实现恰好通过→重构不改行为）。`tdd_enforcement: strict` 配置下，跳步直接被 Reviewer 打回。

**发现**：AI 生成代码的"不爱写测试"倾向被门禁根治——测试从可选项变成闸门；DDL 人工门前置后，测试依赖真实库表而非 mock 幻觉（表结构先于编码存在：stage < 2 被 block，metadata `ddl_done` 置位才解锁）。

### 3.2 测试 T2：异模型只读审查门

**动态输出**：审查 agent 仅允许 Read/Glob/Grep + 只读 git（禁止 Edit/Write/构建命令），与开发 agent 异模型。快速审查 2 分钟 / 全量审查 15 分钟自动路由（改动 < 50 行无 SQL 走快审；≥ 50 行/含 SQL/涉分层/涉表结构走全审；涉保护路径加人工复核）。关卡清单全文见附录 C、附录 D。

**发现（MDM PLM 实战拦截实录）**——审查修复 3 个 Critical：

1. 外部 jar `SpringBootCommon.getUsernumb()` 无 setter → 改用已有 `mdmViewAll_sh_auto`（零扩展零 hack）；
2. N_STATE 字段描述与实际语义失实 → 修正；
3. idList 参数语义不一致 → 统一。

> 注：早期 V2 阶段个别实战（如 PLM 规范层审查）因 gstack 斜杠命令需重启会话，降级为项目内 reviewer 子代理执行——该次审查的"异模型"条件未明示；现行 Multica 阶段 Reviewer 角色经平台配置为**异模型**（harness-agents 角色包 reviewer.md 配置在案：Reviewer=opus、Developer=sonnet，且 Reviewer 严格只读——工具权限不允许改任何代码），降级实例如实保留，机制以现行配置为准。

### 3.3 测试 T3：分级测试 + 浏览器 QA 门

**动态输出**：与 aicoding-browser-qa 技能同源的分级标准——

- **三档深度**：Quick（critical+high，冒烟）/ Standard（+medium，change 级验收，缺省）/ Exhaustive（+low，发布前）；
- **severity 四级**：critical（阻断核心流程/数据丢失/崩溃）→ high（主要功能不可用无绕行）→ medium（可用有明显问题有绕行）→ low（外观小疵）；
- **问题七类**：Visual/UI、Functional、UX、Content、Performance、Console/Errors、Accessibility；
- **每页 8 步清单**：①视觉扫描 ②逐交互点击 ③表单（空提交/非法值/边界）④导航（进出/回退）⑤状态（空/加载/错误/溢出）⑥Console 新增错误 ⑦响应式 ⑧账号边界；
- **健康评分**：基线 100，critical −25 / high −10 / medium −4 / low −1，附 ship-readiness 结论；
- **环境阻塞判定**：验收点菜单不可见或接口报 SEC-00021 → 角色未绑定权限，属环境阻塞非缺陷——记「环境阻塞」节提醒发起人绑定，不进问题清单、不影响健康评分。

Quick 档实际执行报告实例（商品码清洗 change，降级手测模式如实声明，报告字段与本节三档标准逐项对应——证明该标准在实战中被真实执行）。报告原文见附录 G。

**（b）系统运行参数分析**——流水线系统级参数的取值依据与稳定性结论（参数实物出处：openspec-config.yaml、编排配置、治理文档）：

| 参数 | 取值 | 分析结论 |
|---|---|---|
| Developer 并发实例数 | 5 | 写冲突概率随实例数上升，配合排他文件清单兜底——实测稳定上限；超出后冲突重试成本高于并行收益 |
| 兜底巡检周期 | 30 min | 事件通道丢失信号的最长自愈时间窗，与事件驱动秒级接力构成双通道；过短则空耗 token，过长则挂起任务滞留 |
| 连续失败升级阈值 | ≥2 次 | 允许一次瞬时失败自愈重试，第 2 次失败停手 @人——防无限重试烧 token 与错误放大 |
| 连续打回提炼阈值 | ≥2 次 | 同一 task 被打回 2 次判定为"教训曝光不足"，自动触发知识沉淀与晋升红线评估 |
| 快审/全审路由阈值 | 50 行 / 含 SQL / 涉分层 | 与审查时长（2 分钟/15 分钟）匹配的风险分级：小改动走 4 关快审降低成本，结构性改动走 10 关全审守住质量 |
| hotfix 补测时限 | 24 h | 紧急发布通道与"测试不降级"质量门的平衡点 |
| 对账/复盘 cron | 周一 08:17 / 08:23 | 与 */30min 巡检错峰，避免定时任务同点撞车 |
| 浏览器 QA 健康评分权重 | critical −25 / high −10 / medium −4 / low −1 | 严重度量化校准：一个 critical 即扣至 75 分（低于 ship 门槛阈值区），保证阻断级问题不被中低频问题稀释 |

## 4 对软件功能的结论

### 4.1 功能 1：AI 交付代码的质量保障

**能力**：三道质量关（TDD 强制门 / 异模型只读审查门 / 分级测试+浏览器 QA 门）经真实需求验证——单需求 22 项单元测试全部通过（Multica 阶段 41 项复跑全绿）、Critical 问题在审查环节即被拦截、审查结论置信度分级防止 AI 审查误判伤人（高置信 grep 可复现可作打回依据；低置信只列「可能——请人工验证」不得作为打回唯一依据）。

**限制**：存量老代码按降级口径处理（修改处手工验证+显式声明缺口，紧急 hotfix 24h 补测）；浏览器基座缺失时降级代码走读替代页面操作。

### 4.2 功能 2：疑难问题知识沉淀

**能力**：疑难问题四源分类归口（审查打回类 / 测试踩坑类 / 人工测试类 / 运行故障类）全部进入问题库；问题解决技术资料具体到命令级（❌/✅ 对照动作，拒绝空话式教训）。

**限制**：晋升红线必经人类确认，AI 不能自说自话改问题库（人审 MR 才入库）。

## 5 分析摘要（疑难问题库机制）

### 5.1 能力概览

| 能力项 | 机制落地 |
|---|---|
| **提交** | 四源采集：审查打回当场记录（REVIEW.md 关 3/关 9 强制关卡，非可选项）/ 测试踩坑记录（test-report 追加条目）/ 调度巡检对同一问题连续打回 ≥2 次自动提炼 / 周级复盘归因产出草案 |
| **入库把关** | 人审合并 MR 才入库——AI 不能自说自话改问题库；条目拒绝空话，必须具体到命令级：`[YYYY-MM-DD] [change-id] 一句话标题 + ❌ 错误做法（具体到命令/代码形态）+ ✅ 正确做法（具体可执行）` |
| **查询/借鉴** | 双维度检索：按**角色**分文件 `docs/lessons/{角色}.md`（8 角色文件 + index，LIMS 仓库实物在案，全套全文见附录 I）；按**来源 change-id** 溯源（每条目必含 change-id，可反查 openspec/changes/ 工件与 MR）；按**日期**定位（条目必含 YYYY-MM-DD）。各角色**开工必读**，**历史教训视同本级约束执行**；审查抽查"读过了吗"（review-report 中引用条目编号） |
| **共享** | 全角色开放读取；读写分区矩阵（AGENTS.md §7）明确各角色读什么写什么；散落条目归档时统一落盘 |
| **提效/快速开发** | 同类教训第 2 次出现 = 曝光不足 → **自动晋升全员红线**写入宪法，原条目删除——同类坑组织级不再踩 |

**问题库规模统计（截至 2026.11，实物核对口径）**——**闭环率口径：闭环 = 完整闭环条数（原因分析+改善措施+改善结果+复验四要素齐备）/ 总条数 = 10/10 = 100%**（逐条台账见 MDM-pitfalls.md 闭环台账节，全文见附录 I）：

- **疑难问题技术资料 10 条**：MDM 集成踩坑避坑指南（Superpowers / gstack / HyperSpec 集成实战，按"症状→原因→解决"组织，10 条可逐条翻核），典型条目如"TDD 与项目现状冲突：src/test 目录不存在→先建测试骨架再按 TDD 推进""9 关审查一次都过不了：proposal 拆错宁可废弃重开不要硬补"；
- **经教训晋升机制固化全员红线 6 项**：ddl.sql 平铺约束、Windows GBK 传参铁律、MyBatis Map key 大小写、BaseEntity 漏继承、OpenFeign 丢 Header、PageHelper 线程泄漏。实物分布——ddl.sql 平铺约束条款在 LIMS 仓库 `docs/standards/database.md`（实铺详单逐字在案）、MyBatis Map key 大小写（`MapKeyUpperWrapper` 强制 key 大写）与 PageHelper 平台封装（禁止用 com.github.pagehelper 默认实现）条款在 QMS 实铺版 standards/mybatis.md、GBK 传参铁律固化于建区脚手架 `@文件` 传参实现（multica_call.py）；BaseEntity 漏继承、OpenFeign 丢 Header 源自 MDM 实战踩坑记录，随 lessons 机制在各仓库角色文件累积；
- **lessons 角色文件机制实物**：LIMS 仓库 `docs/lessons/{角色}.md` 8 文件（Developer / DevOps / DocKeeper / PM / Prototyper / Reviewer / Tech-Lead / Tester）——其中 Prototyper 角色 7 条实录条目（2026-10，dev server 端口拒连 / 热更新 500 / ux-grid 插槽铁律 / 无头浏览器验证等）为机制实际运行的实例，其余角色文件为机制铺设初期的空模板（条目随踩坑持续追加）。全套文件全文见附录 I。

已沉淀的典型问题解决技术资料（供开发测试人员参考）：ddl.sql 平铺约束（跳板机受限 SQL 入口只认平铺语句）、Windows GBK 乱码（代码页根因 + `@文件` 传参铁律）、MyBatis Map key 大小写、BaseEntity 漏继承、OpenFeign 丢 Header、PageHelper 线程泄漏、集成工具链坑点（TDD 目录骨架 / 审查粒度 / 并发 git 冲突等 10 条）等。

### 5.2 缺陷和限制

存量仓库历史缺口按风险列表声明（哪层没测=什么风险），不粉饰、不一次性追溯；低置信审查结论依赖人工复核闭环。

### 5.3 建议

新仓库从第一天走 harness 流程即无存量缺口问题（TDD 不降级）；存量仓库按模块分批补测。

### 5.4 评价

进化闭环（四源采集 → 人审入库 → 开工必读视同约束 → 同类第 2 次晋升红线、每次晋升必经人类确认）实现"错题本越攒越厚、制度红线越用越硬"，达到设计目标，支撑快速开发模式。

### 双轨审查指南（REVIEW.md）

本项目的代码审查采用**双轨制**：quick-review（快速）+ full-review（完整，基于 gstack）。

#### 审查触发时机

| 时机 | 强制轨道 | 说明 |
|------|---------|------|
| **每个 task 完成** | quick-review | 单 task 自检，~2 分钟 |
| **合并前（Merge / PR）** | full-review | 多 task 协同变更，完整 9 关 |
| **发布前（Release）** | full-review | 影响线上的最后关卡 |
| **热修复（Hotfix）** | quick-review + 人工复核 | 抢时间，但必须事后补 full-review |

**判断口诀**：单 task 走 quick，多 task 走 full；合并/发布必 full。

#### 双轨对比表

| 维度 | quick-review（快速） | full-review（完整，gstack） |
|------|---------------------|----------------------------|
| **耗时** | ~2 分钟 | ~15-30 分钟 |
| **关卡数** | 3 关 | 9 关 |
| **覆盖范围** | 语法 / 测试 / 安全 | 语法 / 测试 / 安全 / 性能 / 可维护性 / 可访问性 / 错误处理 / 依赖 / 文档 |
| **适用场景** | 单 task、小改动（<200 行）| 新功能、架构调整、多 task 协同 |
| **触发命令** | `/quick-review` | `/full-review`（gstack `/review`） |
| **路由规则** | task ≤ 3 自动走此轨道 | task > 3 强制走此轨道 |
| **是否阻塞提交** | 是（任一关失败即阻止） | 是（任一关失败即阻止） |
| **人工复核** | 不要求 | 合并/发布前要求 |
| **依赖工具** | Maven、JUnit | gstack、Maven、JUnit、slop-scan |

#### 9 关完整清单（full-review）

> 参考 gstack `/review` 文档，结合本项目（Java / Maven / Spring）特点裁剪。

##### 第 1 关：语法 / 编译（quick-review 也覆盖）

    private Method trimMethod;

    public void setUp() throws Exception {

## 附录 H：MDM 商品码清洗 change 工件（Multica 阶段实例）

### H.1 proposal.md

#### Why

商品码（C_SPM）在三条写入路径中均可能带首尾空格落库，破坏业务规则：

1. **大视图修改→商品码对应**（`mdmViewAll_update`）与 **基本视图修改→商品码对应**（`mdmViewBasic_update`）：`trim()` 仅用于判空校验，唯一性校验（`C_SPM = #{cSpm}` 精确匹配）、变更检测（newKeys/oldKeys 拼接比较）、insert 均使用原始值。`" ABC "` 与 `"ABC"` 被视为不同值，导致同一商品码可绑定多个物料（UK 索引也拦不住），并可能误判变更、触发多余的先删后插与同步/审核状态重置。
2. **大视图→商品码批量导入**（`mdmViewBasicSpmd_importExcel`）：已对三列做 `String.trim()`，但 Java `trim()` 只去除 ASCII 空白（≤ U+0020），**去不掉全角空格（U+3000）与不换行空格（U+00A0）**——这两个恰是 Excel 复制粘贴与中文输入法的高频产物。

实时校验接口 `mdmViewBasic_check_spmd` 同样使用原始值查询，与保存校验行为需保持一致。

#### What Changes

- `MdmViewManagementServiceImpl` 新增私有 strip 方法：去除首尾 ASCII 空白 + 全角空格（U+3000）+ 不换行空格（U+00A0）
- `mdmViewBasic_update`（~L955）：进入校验循环前将 `cSplx` / `cSpm` / `cBeizhu` 清洗后回写实体，此后判空、列表内去重、全局唯一校验、变更检测、insert 全链路使用干净值
- `mdmViewAll_update`（~L2572）：同上
- `mdmViewBasic_check_spmd`（~L5716）：查询前对入参 strip，与保存校验口径一致
- `mdmViewBasicSpmd_importExcel`（~L5734-5736）：`trim()` 升级为同一 strip 逻辑，堵住全角空格漏洞
- **交付一次性存量清洗 SQL（仅交付，不自动执行）**：定位 C_SPLX / C_SPM 首尾含空白（含全角/不换行空格）的存量记录并清洗
- 前端不改（商品码对应组件维持现状，由后端统一兜底）

##### New Capabilities

（无）

##### Modified Capabilities

- `product-code-mapping`: 商品码对应字段在所有保存路径与实时校验中强制清洗首尾空白（含全角空格、不换行空格）；补充存量数据清洗交付物
- `spmd-batch-import`: 导入解析的 trim 升级为含全角/不换行空白的清洗

#### Impact

- 后端：`MdmViewManagementServiceImpl`（mdmViewBasic_update、mdmViewAll_update、mdmViewBasic_check_spmd、mdmViewBasicSpmd_importExcel）
- 无 Mapper / 表结构变更

### H.4 design.md

#### Context

商品码（`MDM_VIEW_BASIC_SPMD.C_SPM`）有三条写入路径，空格处理现状不一致：

| 路径 | 入口 | 现状 |
|------|------|------|
| 基本视图修改→商品码对应 | `mdmViewBasic_update`（Impl ~L955） | `trim()` 仅判空；唯一校验/变更检测/insert 用原始值 |
| 大视图修改→商品码对应 | `mdmViewAll_update`（Impl ~L2572） | 同上（与上一条代码几乎重复） |
| 大视图→商品码批量导入 | `mdmViewBasicSpmd_importExcel`（Impl ~L5726） | 已 `String.trim()`，但去不掉全角空格 U+3000 与不换行空格 U+00A0 |

实时校验 `mdmViewBasic_check_spmd`（Impl ~L5716）用原始值查询。唯一性 SQL `checkUniqueWithWlbm` 为精确等值匹配（`C_SPM = #{cSpm}`），空格变体击穿唯一性并误触发状态重置。

**约束**：
- 表结构参考 `docs/database/mdm_view_basic_spmd.sql`：`UK_SPMD_SPLX_SPM` 唯一索引 (C_SPLX, C_SPM)；表**无 dUpdateTime**，仅有 TS 时间戳——存量冲突记录无可靠的"新旧"判定依据
- 隐性约定（`docs/architecture/implicit-contracts.md`）：本变更不修改接口返回结构、状态字段语义、默认值语义；变更检测逻辑本身不动，仅其输入值被清洗，无兼容性破坏
- 本变更为旧代码修改（非 harness 新建模块），测试策略按"修改旧代码降级"路径：手工验证 + prepare-review 声明

#### Goals / Non-Goals

**Goals:**
- 三条写入路径 + 实时校验统一清洗口径：首尾 ASCII 空白 + 全角空格（U+3000）+ 不换行空格（U+00A0）
- 清洗发生在校验之前，必填/列表内去重/全局唯一/变更检测/insert 全链路使用干净值
- 交付存量清洗 SQL（含核查语句），由人工执行、人工处理清洗后暴露的冲突

**Non-Goals:**
- 前端组件不改动（后端兜底，用户决策）
- 不做自动去重 / 自动清洗存量数据
- 不处理字段**中间**的空白字符（只动首尾）
- 不改动 Mapper SQL、表结构、接口出入参

#### Decisions

##### D1: strip 实现为 `MdmViewManagementServiceImpl` 私有方法

```java
private String strip(String s) {
    if (s == null) return null;
    return s.replaceAll("^[\\s\\u00A0\\u3000]+|[\\s\\u00A0\\u3000]+$", "");
}
```

- Java 8 的 `\s` 不含 U+00A0/U+3000，必须显式列出
- **备选否决**：`String.trim()`（ASCII only，正是本次要修的漏洞）；`Character.isWhitespace`（含 U+3000 但不含 U+00A0，语义绕）；引入 commons-lang（违反"平台包优先/禁止引入重叠依赖"项目规则）
- 不建公共工具类：当前仅此一个类使用，避免过早抽象

##### D2: 清洗位置 = 校验循环开头回写实体

在 `mdmViewBasic_update`（~L960）与 `mdmViewAll_update`（~L2577）的判空校验 `for` 循环开头执行：

```java
spmd.setcSplx(strip(spmd.getcSplx()));
spmd.setcSpm(strip(spmd.getcSpm()));
spmd.setcBeizhu(strip(spmd.getcBeizhu()));
```

- 回写后，后续判空（`trim().isEmpty()` 判断自然覆盖清洗结果）、列表内去重、`checkUniqueWithWlbm`、newKeys/oldKeys 变更检测、`insertBatch` 全部自动使用干净值——**一处清洗，全链路一致**
- **备选否决**：在各校验点分别 strip（散落多处，易漏，且 insert 仍可能用原始值）；SQL 层 `TRIM()` 匹配（`TRIM(C_SPM) = #{cSpm}` 会使 UK_SPMD_SPLX_SPM 索引失效，且治标不治本）
- 两处 update 路径代码是既有重复结构，按项目现状各加三行，不合并重构

##### D3: `mdmViewBasic_check_spmd` 入参同步清洗

查询前对 `cSplx`/`cSpm` 执行 strip，保证"实时校验说无冲突 → 保存时也无冲突"的口径一致。

##### D4: 导入解析升级为 strip

`mdmViewBasicSpmd_importExcel` L5734-5736 的 `.toString().trim()` 替换为 strip 后的值，其余校验链不动。

##### D5: 存量清洗 SQL 只交付、人工执行

**涉及表与操作**（参考 `docs/database/mdm_view_basic_spmd.sql`）：

| 语句 | 类型 | WHERE 范围 | 索引影响 |
|------|------|-----------|---------|
| 核查 SQL | SELECT（只读） | `C_SPLX`/`C_SPM`/`C_BEIZHU` 首尾含 ASCII 空白、CHR(12288) 全角空格、CHR(160) NBSP 的行 | 无 |
| 清洗 SQL | UPDATE（写 C_SPLX/C_SPM/C_BEIZHU） | 同上，且排除"清洗后变为空"的行 | UPDATE 维护 `UK_SPMD_SPLX_SPM` 唯一索引；若清洗后与已有组合重复 → **ORA-00001 直接报错** |

- Oracle `REGEXP_REPLACE(col, '^[ ... ]+|[ ... ]+$', '')` 实现首尾清洗，字符类含 `' '`、`CHR(9/10/13)`、`CHR(160)`、`CHR(12288)`
- **边界**：值为纯空白的行清洗后变 NULL，违反 `C_SPLX/C_SPM NOT NULL` 约束 → 清洗 SQL 的 WHERE 显式排除（`TRIM(...)` 非空条件），此类行由核查 SQL 单独暴露，人工删除
- **冲突处理（人工）**：执行中 ORA-00001 时，用核查 SQL 定位 trim 后重复的组合，人工决定保留哪条（表无 dUpdateTime，不能按时间自动判定），删除后重跑
- 交付物放 `docs/database/` 下的 SQL 说明文件，不进 `src/main/resources/db/`（受保护目录，且不由应用执行）

#### Risks / Trade-offs

- [清洗后暴露存量重复，UPDATE 报 ORA-00001] → 预期行为；核查 SQL 提前发现，人工处理后重跑；交付文档写明操作步骤
- [纯空白值的脏行清洗后违反 NOT NULL] → WHERE 排除 + 核查 SQL 单独暴露，人工删除
- [前端不清洗，用户在界面上仍看到自己输入的空格] → 后端落库为干净值，重新打开即正常；用户已确认接受
- [正则每次编译的开销] → 行数为个位数级（商品码列表），可忽略；如需优化可预编译 Pattern，暂不做
- [check_spmd 与保存校验仍有极小时间窗] → 既有行为，不因本变更恶化

#### Migration Plan

1. 后端发版（增量清洗生效）
2. 人工执行核查 SQL → 确认量级与冲突组合
3. 人工处理冲突（删除/修改重复行）
4. 人工执行清洗 SQL
5. 回滚：代码回退即可；清洗 SQL 为数据订正，回滚依赖执行前人工备份（文档中提示先 `CREATE TABLE ... AS SELECT` 备份）

#### Open Questions

（无——strip 范围、前端不动、人工清洗三个决策均已确认）

### I.1 MDM-pitfalls.md（MDM 集成踩坑避坑指南，10 条闭环台账）

### 10 条血泪教训（Superpowers + gstack 集成坑点）

> 这是集成 Superpowers / gstack / HyperSpec 时的避坑指南。
> 每条都是真实项目踩过的坑，按"症状 → 原因 → 解决"组织。

---

#### 1. 装完 Superpowers 就忘了改 config.yaml

**症状**：对话开始时 AI 不调用 `using-superpowers`；tasks 没有强制 2-5 分钟粒度。

**原因**：skills 默认是 on-demand 触发，没有强制"会话开始时自检"。

**解决**：

- 在 `CLAUDE.md` 加 "Superpowers 元技能自检" 段（**已做**）
- 在 `openspec/config.yaml` 的 `context` 加 2026-06 增量段（**已做**）
- 跑 `/superpowers:using-superpowers` 验证输出包含 always_active skills

#### 2. gstack 子代理没有用户上下文

**症状**：`gstack /review` 给出"通用化"建议，与本项目 baseframe 平台包冲突（如建议引入 Redisson 替代 `sunny-base-lock`）。

**原因**：gstack 子代理不知道项目有 baseframe 自研包。

**解决**：

- 在 `.claude/skills/gstack/skills/*/SKILL.md` 中注入项目 context（人工编辑或 hook 注入）
- 或在 `gstack /review` 命令前先说一句："本项目使用 sunny-base-* 自研包，禁止引入重叠依赖"

#### 3. TDD 与项目现状冲突

**症状**：强制 TDD 时发现 `src/test/` 目录不存在，写测试找不到父类 / 配置。

**原因**：`spring-boot-starter-test` 已在 pom.xml，但实际从未建过 `src/test/java/`。

**解决**：

- 第一次 TDD 任务时**先建立测试目录骨架**（标准 Maven layout）：
  ```
  src/test/java/
  src/test/resources/
  ```
- 写入 `application-test.yml`（用 H2 内存库或 Testcontainers 替代 Oracle）
- 后续任务按 TDD 推进

#### 4. /opsx:verify 与 gstack /review 重复检查

**症状**：9 关审查中规范对齐和通用代码质量都跑一遍，发现大量重复警告。

**原因**：两者关注点有重叠（都在看代码）。

**解决**：

- 明确职责分工：
  - **`/opsx:verify`** 看"实现 vs OpenSpec 工件"（proposal 范围 / tasks 覆盖）
  - **`gstack /review`** 看"代码质量"（命名 / 重复 / 复杂度）
- 跑顺序：先 `/opsx:verify`（如失败，根本不进入 `gstack /review`）

#### 5. 2-5 分钟粒度被一刀切

**症状**：所有 task 都被强制拆到 2-5 分钟，但有些任务（如"修改 yml 配置"）本身就是 1 分钟的事，强行拆细反而冗余。

**原因**：粒度规则过于死板。

**解决**：

- 2-5 分钟是**目标**而非硬规则
- 简单任务（配置 / 文档 / 注释）可以 < 2 分钟
- 复杂任务（Service 业务）必须 ≥ 2 分钟粒度
- writing-plans skill 会自动判断

#### 6. 子代理并发跑导致 git 冲突

**症状**：多个子代理同时 commit，`git push` 时出现 rebase 冲突。

**原因**：子代理默认并行执行。

**解决**：

- 在 `subagent-driven-development` 中**强制串行**（`--serial` 标志）
- 或在 commit 前加 git lock 文件

#### 7. gstack /qa 找不到测试数据库

**症状**：`gstack /qa` 报"无法连接 oracle 测试库"。

**原因**：本地没有 Oracle，CI 才有。

**解决**：

- 短期：跳过 `gstack /qa`，用 `/prepare-review` 手工验证
- 长期：CI 集成 Testcontainers（Oracle in Docker）

#### 8. 9 关审查一次都过不了

**症状**：第一次跑 9 关，前 3 关都失败，循环多轮。

**原因**：tasks 粒度不够、OpenSpec proposal 边界不清。

**解决**：

- **第一版 proposal 通常只是草案**（Harness.md 实战经验第 1 条）
- 如果 proposal 拆错，**宁可废弃当前 change 重开**，不要硬补

### Prototyper · 原型链踩坑录

> 按角色自建自维护；每条 = 现象 → 根因 → 解法。新坑追加在文末，不改旧条。

#### 1. dev server 端口 6000 被 Chrome 拒连（ERR_UNSAFE_PORT）

- **现象**：vite 起在 6000，curl 通、浏览器直连报 `ERR_UNSAFE_PORT`。
- **根因**：Chromium 系把 6000–6063 列为 X11 保留端口，客户端直接拒连；服务端探测正常，极易误判成服务没起。
- **解法**：端口从 6000 起避用 6000–6063，本工程固定 6100；详录见 `sunny-lims-prototype/SERVICE.md`。

#### 2. `<script lang="jsx">` 的 SFC 热更新后整页 500 / 浏览器停留在旧模块（R7b+R7c，2026-10-22）

- **现象**：页面首次加载正常；HMR 后 lang.jsx 页面在浏览器里报 babel「Unexpected token (6:6)」（code frame 是**模板**的 `@事件` 行）或 import-analysis 500——**用户看到的永远是旧版本页面**，极易误判成「代码改了没生效」。
- **根因**（两层，都要修）：
  1. **HMR `?t=` 后缀 vs include 正则**：HMR 给模块 URL 追加 `?t=时间戳`，`vue2-jsx` 插件 include 写 `/\.[jt]sx$/`（只匹配结尾）不再命中 → JSX 不转换 → 500。解法：include 容忍查询串 `/\.[jt]sx([?&]|$)/`。
  2. **@vitejs/plugin-vue2 脚本子模块竞态**：`xxx.vue?vue&type=script&lang.jsx` 的 load 走 `getResolvedScript(descriptor)`（WeakMap，仅由主模块 transformMain 填充）——主模块尚未转换时返回 undefined → vite 落到 fs 兜底把**整个 SFC** 当模块代码 → babel 把模板当 JSX 解析报 (6:6)。**启动首请求、编辑后 HMR 直取子模块时必现**。解法：vite.config 里加 `enforce: 'pre'` 的 load 插件直接返回 script 块内容（注意 vue 2.7 的 `compiler-sfc.parse({source,...})` **直接返回描述符本体**，不是 `{descriptor}` 包装）。
- **教训**：判断「改了没生效」先分清：curl 该模块 URL（带/不带 `?t=` 都试、冷启动直取子模块）看 transform 是否 200 → 再怀疑业务代码。HMR 徽标绿 ≠ 当前页面模块是最新的。

#### 3. umy-ui ux-grid 操作列 push 后不渲染（R7b，2026-10-22）

- **现象**：页面 `state_init()` 里往 `tableAttrs.columns` push「操作列」列，表格里始终不出现。
- **根因**：umy-ui ux-grid 对 `columns` 的 watch 是**引用变化**才 `loadColumn`（`watch: { columns(e){ nextTick(loadColumn(e)) } }`），`push` 原地变更在 created→mount 时序竞态下不触发。
- **解法**：改完列后换一次引用强制重载：`this.<模块>.tableAttrs.columns = this.<模块>.tableAttrs.columns.slice()`。另注意列按钮要从 `tableAttrs.columnTableAttrs` 取（官方 queryListTemplate 同款路径），不是模块 state 根上。

#### 4. umy-ui 单元格插槽两条铁律（R7d，2026-10-22，无头浏览器实测定案）

- **现象**：列插槽 `default` 里渲染 el-tag/按钮，表头在、单元格空白（td 的 title 兜底露原始值）。
- **铁律**：
  1. **h 必须用 umy 调用插槽时传入的第 2 参数**：`default: ({ row }, h) => [...]`。页面实例 `$createElement` 造的 vnode 上下文与表格渲染管线不符，**会被静默丢弃**（无任何报错）——实测 span/el-tag 均空白。
  2. **必须返回 vnode 数组** `[h(...)]`，裸 VNode 渲染为空（官方模板/utils.js 的 spanselect 插槽全都是 `[<span>…]` 数组返回，当初照抄 JSX 时丢了这层语义）。
- **教训**：这类「组件库内部调用约定」问题，静态读源码推不出全部行为（本轮连错三轮）；**上无头浏览器（browse skill）跑真实页面 + 运行时逐步换插槽做 A/B 实验**，10 分钟定案。另：umy 表格横向虚拟滚动，**屏外列不渲染**——验证右侧列时先滚动过去再断言。

#### 5. 无头浏览器渲染验证当默认步骤 = 每轮白烧 3 分钟（2026-10-27）

- **现象**：起服后顺手跑一遍无头 Chrome（实渲染 + `--dump-dom` + console 抓取 + 截图）当"验证"，一轮 ≈3 分钟，占起服时长的绝大部分。
- **根因**：第 4 条（无头浏览器定案 umy-ui 插槽）被当成了**每轮默认流程**。但它的适用场景是**排错取证**——组件行为反常、需要 A/B 实验时；不是"服务起好了吗"的判据。起服是否成功，用入口页 + 入口模块的 HTTP 200 就够了，渲染验证解决的是另一个问题。
- **解法**：把就绪判据**内建进注册脚本**（`sunny-lims-prototype/scripts/register-dev-task.ps1`）：回收端口 → 注册点火 → 入口页/入口模块双地址 200 → 占端口 PID 归属校验，阻塞到 READY，耗时 ≈13–25 秒；`logs/health-check.json` 的 `ready:true` 即交付门槛。**无头浏览器降级为按需取证**——仅①用户要截图/录屏 ②疑似白屏或表格空（模块 200 但渲染异常）③定稿前留证据 三种情形才跑。
- **教训**：**验证要分"服务活着"与"页面正确"两层**，前者必须便宜且默认，后者昂贵且按需。把昂贵验证塞进默认流程，等于每轮都在为一个不常失败的问题付钱。

#### 6. 删计划任务不会停运行实例 → 新实例静默漂端口 → 交付的地址指向旧页面（2026-10-27）

- **现象**：重跑注册脚本"重启"服务，脚本自检全部通过（6100 返回 200），但用户打开地址看到的是**上一版页面**；实际新实例起在 6102（6101 被占），而交付地址报的是 6100。
- **根因**：Windows `Schedule.Service.DeleteTask` **只删注册项，不停已运行的实例**——旧 vite 继续占着 6100。新实例因端口冲突被 vite **静默漂移到下一个可用端口**（vite 默认不 `strictPort`），而双地址探测"6100 有响应"——响应的是旧实例，自检被**骗过**。
- **解法**：三处同时修——
  1. 注册前先 `$t.Stop()` 再 `DeleteTask`（停实例而非只删注册项）；
  2. 回收**本工程路径**下的残留 vite 进程（按精确 PID，先与 `multica daemon status --output json` 的 pid 比对再动手，**不按进程名杀**）；
  3. vite 加 `strictPort: true`——端口被占直接失败退出，不静默漂移；自检另加**实例归属校验**（占端口的 PID 必须是本工程 vite），不匹配就报 DIAG 而非交付。
- **教训**：**"地址能访问"不等于"访问到的是我刚起的那份"**。双地址验证只证明了有东西在应答，没证明应答者是预期的那个。凡是"重启后行为异常"，先查端口归属与进程 PID，不要先怀疑代码。

#### 7. 端口写死 = 迟早撞车；随机分配要跨任务互斥 + OS 实测 + 复用（2026-10-27）

- **现象**：原型 dev server 固定用 6100。同机实测已有 **2 个 Multica 任务各起着一个 vite**（6100 / 6102），还各有同名计划任务；再来一个任务就撞。
- **根因**：端口是**机器级资源**，但每个 checkout 的代码副本都以为 6100 是自己的。写死端口 = 把"现在恰好空着"当成了常量。
- **解法**（`sunny-lims-prototype/scripts/allocate-port.mjs`）：区间 6100–6299 内随机取，三重判占用才给——
  1. **剔除 6000–6063**（Chromium 拒访，服务端 curl 却通）；
  2. **跨任务互斥**：`~/.sunny-lims/ports/port-<端口>.lock` 用 `open(O_EXCL)` 原子创建；
  3. **OS 实测**：逐个真实 bind 试探，能发现看不见的占用方。
  再加**重拉复用**：本 checkout 上次的端口仍空闲就继续用——**地址不能漂**，用户已打开的页面不能失效。
- **三个必须避开的坑**：
  1. **锁文件不能放 `os.tmpdir()`**——Multica 运行时把 `TEMP` 指向 `Temp\multica-task-<id>` 子目录，**每个任务各拿一个目录**，锁就形同虚设。要放用户级（`os.homedir()`）目录。
  2. **计划任务名也要唯一**——否则并发任务互相覆盖任务定义。命名带 checkout 后缀（项目路径 sha1 前 8 位）；旧固定名只能靠**动作的 WorkingDirectory 是否等于本工程路径**判定归属，别人的任务不能动。
  3. **端口漂移是隐蔽故障**——vite 默认不 `strictPort`，端口被占就静默换端口，于是"6100 能访问"探到的是旧实例。必须 `strictPort: true` + 实例归属校验（占端口的 PID 必须是本工程 vite）。
- **教训**：**机器级共享资源（端口、锁、缓存）不能用"本工程路径下的文件"来隔离**——每个 checkout 都是独立副本，隔离必须建立在机器级位置 + 操作系统事实上。
