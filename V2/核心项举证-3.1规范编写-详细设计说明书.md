## 1 引言

### 1.1 编写目的

本说明书详细定义"机器可执行软件规范库"的构成、条款与执行机制，作为规范库建设、使用与推广的权威依据，及核心项 3.1 的举证材料。预期读者：评审评委、公司 IT 相关岗位（开发/测试/运维）。

### 1.2 背景

在建设 AI 多 Agent 编码 Harness 过程中发现：传统"给人看"的规范无法约束 AI 行为——提示词可被绕过、执行靠自觉。为此设计编制了一套**机器可执行**的规范库：四级规范覆盖编码、数据库、测试、部署、维护全维度，配套三重强制执行机制，已在公司 IT 六个业务系统仓库铺设沿用。

## 2 规范库总体设计

### 2.1 总体构成

| 规范 | 定位 | 覆盖维度 | 篇幅 |
|---|---|---|---|
| **CLAUDE.md（项目宪法）** | 全员红线 | 编码+部署+维护 | 15 节 |
| **AGENTS.md（协作总纲）** | 协作制度 | 协作+变更管理+维护 | 7 节 |
| **REVIEW.md（审查关卡）** | 质量门禁 | 测试+审查 | quick 4 关 + full 10 关 |
| **standards/（技术详单）** | 操作标准 | 编码+数据库+测试 | java / mybatis / spring / naming / testing 五篇 |

### 2.2 两级结构设计方法

"红线一句话进宪法、详单进 standards/"：宪法只保留可速读的红线（如 §11 命名只写一句话红线），字段级详单全部下沉到 standards/ 并与宪法两向引用——避免单文件膨胀失效。规范内容按目标仓库逐条以**代码证据填充**（16 项结构化占位符，每条须有代码证据、禁止编造），保证规范与仓库实况一致而非泛泛模板。

## 3 程序单元 1：CLAUDE.md 项目宪法

### 3.1 程序描述

进入仓库的任何 agent（及开发者）的首要约束文件，开工必读。

### 3.2 功能

15 节目录：§0 适用范围 / §1 项目定位 / §2 模块结构表 / §3 通信与基础设施 / §4 构建命令 / §5 构建工具路径约定 / §6 OpenSpec 工作流 / §7 TDD 强约束 / §8 分层规则 / §9 平台包优先级 / §10 保护目录 / §11 命名约定 / §12 统一响应格式 / §13 日志规范 / §14 平台能力帮助 / §15 文档体系入口。

### 3.3 条款原文摘录（一）：§6 OpenSpec 工件流（强制顺序）

> | 顺序 | Artifact | 核心问题 |
> |------|----------|----------|
> | 1 | proposal | WHY — 为什么做 |
> | 2 | specs | WHAT — 做什么 |
> | 3 | design | HOW — 怎么做 |
> | 4 | tasks | 执行 |
>
> **判断口诀：先需求后设计，先 WHAT 后 HOW。** 即使多个 artifact 同时 ready，也必须先 specs 后 design。

### 3.4 条款原文摘录（二）：§7 TDD 强约束（5 步红绿循环）

> 1. 写失败测试 2. 确认测试失败 3. 实现代码 4. 确认测试通过 5. 提交
>
> `openspec/config.yaml` 中 `tdd_enforcement: strict`，跳步会被 Reviewer 打回。

### 3.5 条款原文摘录（三）：§10 保护目录（写入会被 hook 拒绝）

> 以下路径禁止 Edit/Write，由 `.claude/hooks/guard_write.py` 拦截：`application*.yml` / `db/` / `sql/` / `settings.xml` / `pom.xml`。
> 如需变更，必须在 `design.md` 中显式声明，并经 Reviewer 审核通过。

### 3.6 限制条件

宪法红线条目增删须经教训晋升机制的人类确认环节（见 §8 进化机制），不可随意扩写。

## 4 程序单元 2：AGENTS.md 协作总纲

### 4.1 程序描述

多 Agent（及人）在同一个 change 上协作的制度总纲。

### 4.2 功能（7 节）

角色职责 / Git 策略 / 工件结构 / 变更联动矩阵 / 教训机制 / 读写分区矩阵 / 工作流入口。

### 4.3 条款原文摘录（一）：§4 Git 策略（分支级权限）

> - 每个 change 在 `feature/{change-id}` 上工作，所有 agent 的产物 commit 都打到这条分支
> - 开工先 `git fetch origin`，基于最新 `origin/master` 创建 feature 分支
> - `master` / 目标分支禁止直推，只能经 MR 由人类合并
> - 工件 commit 后**必须立即 push**——未 push 的本地分支在其他 runtime 拉不到，跨机协作会断链

### 4.4 条款原文摘录（二）：§6 变更联动矩阵（本规范的特色设计）

| 触发 | 下游义务 | 执行方式 |
|---|---|---|
| PM 修改 proposal（已 in_review 后） | PM 串联返工 specs + design | Mika 把下游所有 stage 子 issue 置 blocked，等重做解锁 |
| PM 修改 specs/design | Tech-Lead 必须 re-tasks | 同上 |
| PM 产出 ddl.sql | **人工执行 DDL 后流程才可继续**；受影响域数据库文档须在本 change 内重生成 | 人执行后评论回执 @Mika；tasks.md 必含文档重生成 task |
| Developer 实施发现 design 漏字段 | 反向触发 PM（**不得擅自扩边界**） | 评论 + blocked + @Mika 决定是否回退 |

## 5 程序单元 3：REVIEW.md 审查关卡

### 5.1 程序描述

代码审查的质量门禁清单，按变更风险自动路由审查深度。

### 5.2 功能：触发条件分级路由

| 场景 | 路径 | 关卡数 |
|---|---|---|
| 改动 < 50 行，无 SQL，无架构变化 | quick-review | 4 关 |
| 改动 ≥ 50 行 / 含 SQL / 涉及分层 / 涉及表结构 | full-review | 10 关 |
| 涉及 protected 路径 | full-review + 人工复核 | 10 关 + 人类 |

**quick-review 4 关**：①spec-align（规约对齐：改动是否在 task 范围内、有无"顺手改"）②risk-check（风险：是否触保护目录/新依赖/公共字段）③lesson-check（经验命中：问题是否命中已有教训条目、是否产生新教训、抽查是否读过）④archive（归档准备）。

**full-review 10 关**：①verify（OpenSpec 四件套校验）②review（通用代码审查：命名/幻觉式重命名）③架构分层审查 ④数据访问/SQL 审查 ⑤security（安全）⑥simplify（简化+AI 冗余）⑦qa（质量）⑧prepare-review（摘要）⑨lesson-check ⑩archive。

### 5.3 算法：专为 AI 生成代码设计的审查项（节选原文）

> **关 5 security（节选）**
> - [ ] **LLM 信任边界**：外部返回 / LLM 产出 / 第三方数据是否未经结构·类型·范围校验直接入库或参与执行？
> - [ ] **条件副作用**：同一条件分支内是否混合了校验逻辑与写操作（副作用应与校验分离）？

> **关 6 simplify — AI 冗余物（AI 生成代码高发坏味道，重点排查）**
> 过度防御（catch 后吞异常或不必要的空判）/ 死代码与永假分支 / 无用注释堆砌（复述代码的"Generated"式注释）/ 同一抽象重复发明（仓库已有工具类又写一个）/ 幻觉式重命名引用不存在的既有方法

### 5.4 输出项：结论置信度分级（防止 AI 审查误判伤人）

| 置信度 | 判据 | 动作 |
|---|---|---|
| 高 | grep / 只读命令可复现的证据 | 直接定论，可作打回依据 |
| 中 | 模式聚合 / 启发式推断 | 标注「存疑」列出，允许一定噪声 |
| 低 | 需理解视觉/业务意图才能确认 | 列为「可能——请人工验证」，**不得作为打回唯一依据** |

### 5.5 限制条件

打回必须附「打回原因 + 修改建议（文件:行号）+ 重新提交条件」三段式；同一 task 连续 2 次打回自动升级人类 reviewer。

## 6 程序单元 4：standards/ 技术详单（五篇）

### 6.1 程序描述

字段级操作标准，覆盖编码（java/spring/mybatis/naming）与测试（testing）。

### 6.2 功能与特色条款

**java.md / spring.md / mybatis.md / naming.md（编码与数据库语言规范）**：分层与命名约定、平台包优先级、Mapper 变更检查清单。特色条款源自真实踩坑固化：

> ddl.sql 一律平铺 SQL 语句逐条分号结尾（触发器后不加 `/`），**禁止 PL/SQL 匿名块（DECLARE…BEGIN…END）/ EXECUTE IMMEDIATE / DBMS_OUTPUT / 存在性预检查**——执行通道常为跳板机受限 SQL 入口，只认平铺语句。

**testing.md（测试规范）**：新旧代码口径（存量测试状况**禁止粉饰**、新代码 TDD 不降级、旧代码修改降级条件、紧急 hotfix 24h 补测时限）/ mock 边界（**被测对象禁止 mock 自己证明自己**）/ 集成测试 / 浏览器 QA 三档标准 / 禁止的反模式 / 未测试缺口声明模板。

**api.md 接口设计规范**（并入宪法 §12 与详单）：「历史命名包袱清单——禁止改的前端硬依赖逐条列出」；change 级契约条款——PM 逐接口列 method/path/权限/请求参数/响应结构/错误码，无接口变更显式写「本变更无接口改动」不留空；**契约先行：后续改接口必须先改 api.md 再改代码**。

### 6.3 存储分配

规范库随治理骨架（skeleton/ 20+ 文件）铺设进每个目标仓库 docs/ 与根目录，进 Git 版本管理。

## 7 接口：规范强制执行机制（从"文档"到"机器可执行的制度"）

| 机制 | 实现实物 | 效果 |
|---|---|---|
| 开工必读 | 各角色开工先读宪法+总纲，历史教训视同本级约束执行 | 规范从"参考"变为"前提" |
| 程序拦截 | guard_write.py（PreToolUse 钩子，60 行 Python）——保护路径写入直接 block | 禁改清单零违反，物理不可绕过 |
| 关卡校验 | openspec/config.yaml：`tdd_enforcement: strict` + `ordering: strict`；REVIEW.md 10 关 | 执行留痕、可审计 |

**openspec/config.yaml 全文摘录**（`files/治理文件实物/openspec-config.yaml`）：

```yaml
schema: spec-driven
tdd_enforcement: strict
ordering: strict
model_routing_hints:
  explore: haiku
  propose: opus
  apply: sonnet
  review: opus
protected_paths:
  - "**/application.yml"
  - "**/application-*.yml"
  - "**/db/**"
  - "**/sql/**"
  - "**/settings.xml"
  - "**/pom.xml"
```

## 8 系统维护设计：规范库运维与进化机制（保证 3 年内持续有效）

1. **防漂移双保险**：变更随行（宪法 §15：文档随 change 同步更新，**不允许「事后补文档」**）+ 周级自动对账兜底（aicoding-harness-audit autopilot）；
2. **自我进化**：同类教训第 2 次出现自动晋升写入宪法/审查关卡成为全员红线，原条目删除——规范库随使用越来越严密，而非逐渐过时；每次晋升必经人类确认；
3. **跨仓库复用**：治理层骨架作为"结构权威源"（20+ 文件），对齐模式铺设到任意仓库（补缺节、不覆盖定制），新仓库全套规范铺设约半日。
