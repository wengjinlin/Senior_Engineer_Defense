三、需要你拍板的 4 个决策点

决策 1：多条变体的失败策略 ⚠️ 最关键

入参 MDM_VIEW_VARIANT 是数组（示例有 3 条）。如果其中 1 条在第三层失败（变体代码不存在），另外 2
条已处理过的怎么办？

┌──────────────────┬──────────────────────────────────────┬───────────────────────────────────────┐
│       方案       │                 行为                 │               适用场景                │
├──────────────────┼──────────────────────────────────────┼───────────────────────────────────────┤
│ A.               │ 1 条失败 → 全部回滚 + RETURN TYPE=E  │ PLM                                   │
│ 原子事务（推荐） │                                      │ 侧重数据一致性，要么全成功要么全失败  │
├──────────────────┼──────────────────────────────────────┼───────────────────────────────────────┤
│ B. 部分成功      │ 每条独立                             │ PLM 侧重"尽量多救活"，但 RETURN       │
│                  │ try/catch，失败的回报错，成功的保留  │ 结构只支持 1 条                       │
└──────────────────┴──────────────────────────────────────┴───────────────────────────────────────┘

用户原话"回滚第四层的 物料+变体代码+需求管控+状态 的维护"暗示是单条变体维度的回滚——但 RETURN
是单条，推测实际希望整批原子（A 方案）。需要你确认。

决策 2：审核物料的报错返回方式

用户说"审核物料，且返回视图审核的报错"。现有 po_zt_fail_all() 把物料状态改为"审核失败"，但不抛异常。

┌────────────────────────────────────────────────────────────────────────┬────────────────┐
│                                  方案                                  │      行为      │
├────────────────────────────────────────────────────────────────────────┼────────────────┤
│ A. po_zt_fail_all 执行后，无论其内部有无异常都返回成功（忽略审核结果） │ 简单           │
├────────────────────────────────────────────────────────────────────────┼────────────────┤
│ B. po_zt_fail_all 若失败，RETURN TYPE=E + MESSAGE=审核报错             │ 严格按用户描述 │
├────────────────────────────────────────────────────────────────────────┼────────────────┤
│ C. po_zt_fail_all 一定成功（内部不会失败），无需返回报错               │ 看实际实现     │
└────────────────────────────────────────────────────────────────────────┴────────────────┘
