## 七、十题答辩口径（答辩人视角）

> 说明：以下口径基于报告 PDF 已有证据作答；PDF 无数据支撑处标注 **【答辩前需补】**，需用 git / GitLab 实测数据填充后再上场，不可虚构。

### Q1. 节约测算口径（684 万重算）

**答辩口径：**

"684 万/年我在报告里已明确标注为'等价产能释放空间'——测算假设是六系统月均 190 个交付单元**全部**经平台开发。实际现状是：体系 2026.04 才上线、当前处于分批推广期，直接按当前实际占比重算，数字会明显小于 684 万，这点我不回避。

但请看三组实测基础：①六系统 git 全历史 5,904 个 merge 交付单元（月均 190）是真实需求量底座；②**ECQ 是'生而经平台'的样本**——2026.08 建仓起全量走平台开发，2026.08—10 已交付 70 个交付单元、月均 32 个，这是'全部经平台'口径的现实锚点；③单需求节约（bugfix 0.8 人天 / 小需求 1.7 人天 / 中大需求 4.5 人天）来自平台前后人天实测对比，不是估算拍脑袋。

我的主张是：684 万是推广完成态的稳态产能空间，ECQ 月均 32 个交付单元证明该稳态在单系统上已实现；随着其余五系统需求逐步切换到平台（新仓库全套规范铺设约半日），实际兑现比例会逐季抬升。"

**【答辩前需补】**：各系统 2026.04 后经平台（走 change 工件流）的 MR 数 / 该系统同期总 merge 数，做成一张六行占比表带上。

### Q2. "30 分钟"拆解

**答辩口径：**

"两个口径要分开：**30 分钟指 AI 端到端执行链**（建单→五阶段→MR 就绪），**人的净投入是另一组数**——bugfix 约 1.5 小时、小需求约 2.5 小时、中大需求约 4 小时，构成是 chat 澄清 + G1 审四工件/执行 DDL + G2 审 MR，AI 执行时间不计人天。

墙钟时间用实例说话：商品码清洗 change，分支首 commit 2026-09-21 10:06，四工件+代码+测试+文档（10 files + 431 行）**当日全部完成**。如果 G1/G2 人工审查排队，墙钟确实会拉长——但关键区别是：AI 执行阶段人完全释放，可以并行处理其他需求的 G1/G2。传统模式一人串行跟一个需求，平台模式一人可同时当多个需求的决策者，这是产能杠杆的来源，而不是单点 30 分钟。"

**【答辩前需补】**：调出该 change 的 issue 评论时间戳链（建单评论→G1→MR），现场可逐条对表。

### Q3. 产能是否真的释放（上线前后对比）

**答辩口径：**

"分三层回答：

第一层，全历史均值不能直接对比——QMS 月均 44 是 2023.05 起的均值，其中两年半在平台之前。上线后（2026.04—11）QMS 服务端的月均交付数我带数据来（见附表）。**【答辩前需补】**

第二层，已有的产能实证：①ECQ 作为全量经平台的新系统，月均 32 个交付单元；②MDM 本人 MR 节奏——V2 阶段 4 个月 8 个 MR、Multica 阶段 4 个月 6 个 MR，这是**一个人单线**的持续产出；③六系统月均 190 个交付单元的需求池在正常消化，没有积压恶化。

第三层，最诚实的产能证据是人的投入比：传统小需求 2 人天 vs 平台 0.3 人天。产能释放不必然表现为'交付量翻倍'——也可能表现为'同等交付量下人力转向更高价值工作'（需求分析、业务线体探索），我的报告口径正是'工时口径的等价产能释放，非人员裁减'。"

### Q4. 自研深度与开源依赖风险

**答辩口径：**

"自研面集中在三层，一层都不在开源件内部：

①**编排层**——事件驱动'完成评论'信号、issue 描述作为唯一权威源、失败分级升级（连败 2 次找人、被连续打回 2 次转知识沉淀），这些调度逻辑全部自研；②**治理层**——四级规范库（宪法 16 节/协作总纲/审查关卡/技术详单）、guard_write.py PreToolUse 拦截钩子（PROTECTED_PATTERNS + decision:block）、ordering:strict 工件顺序门禁、错题本四源采集与晋升机制；③**技能层与脚手架**——8 个业务技能、6 个一键建区脚手架（幂等、断点续传）。

依赖风险的答案在架构设计里：我在技术路线规划时即做了**多 CLI 适配（opencode/Qwen）**——CLI 是可替换插槽，不是绑定。更关键的是：**治理层落在目标仓库侧（Git 平台 + CLAUDE.md/钩子），与任何单一 AI CLI 完全解耦**——Claude Code 明天消失，规范库、门禁、错题本、建区脚手架原样工作，换个 CLI 执行体即可。这也是选型时'复用成熟件、自研压缩到编排+治理+技能薄层'的初衷：把自研投在不可替代处。"

**【答辩前需补】**：自研代码行数统计（编排/治理/技能/脚手架分项）。

### Q5. 异模型审查实证

**答辩口径：**

"机制先说清：审查 agent 用**另一个家族的模型**、**只读权限**（无写权）、专为 AI 代码设计的审查项（LLM 信任边界、AI 冗余物）——三重防共谋设计。

实例我带 GitLab 记录来：审查打回是疑难问题库四源采集的第一源，'整理 AI 代码审查质量问题提交处理'是报告 3.3 的原话。**【答辩前需补：调取 2-3 个具体 MR 打回记录——含打回原因（如 LLM 信任边界违规/AI 冗余物/幻觉依赖）与修复 diff】**

同时不夸大这道关：异模型审查是三道质量关的第二道，前面有 TDD 强制门（考试不过不出厂），后面有分级测试+浏览器 QA。单点拦截率不是关键，**纵深的漏过概率**才是——目前红线文件 32 个月零违反。"

### Q6. 三重漏网兜底

**答辩口径：**

" Developer 写错、审查者漏过、测试未覆盖——这个场景我在设计时就假设会发生。答案有两道：

**事前**：G2 人审门——任何代码不经人审合不进 master，人握最终决策权，这是设计原则'AI 干活、人拍板'的底线；高危动作（数据库脚本）从一开始就人工执行，AI 碰不到。

**事后**：Git MR 铁律——合并时间戳不可篡改，revert 一个 MR 即精准回滚；三条自动巡检（30 分钟兜底巡检/每周文档对账/每周测试复盘）提供周期性稽核；逃逸缺陷复盘后经四源采集进错题本，同类第 2 次出现晋升全员红线——**同一个坑没有第三次机会**。

诚实说：任何体系都不能保证零缺陷，我的设计目标不是'缺陷不发生'，而是'缺陷逃不出**可追溯、可回滚、可进化**的边界'。32 个月运行、红线零违反是这个边界的实证。"

### Q7. 团队边界

**答辩口径：**

"直接划界：

**本人亲手做的**：四代架构设计与全部核心机制（编排信号/SDD 工件链/TDD 门禁/guard_write 硬约束/错题本机制）、四级规范库骨架与三重强制执行、6 个一键建区脚手架、技术路线选型与多 CLI 适配、五层性能瓶颈定位调优——报告 9 条行为要点的角色栏与此一一对应，QMS 89%、MDM 95.5% 的提交占比是 git 佐证。

**团队协同的**：8 个业务技能中的前后端部分技能（报告原文'前后端技能由团队协同建设'）；六系统推广中，本人深度落地 MDM/QMS，LIMS/ECQ 等由同事按脚手架半自助接入——**这恰恰是平台化的成功标准**：新系统接入从'依赖我 4-6 天'变成'同事半日自助'，如果所有接入都必须我亲手做，那它就不是平台而是我的手艺。

**可持续性**：四代演进文档+6 篇技术文档+README 已完备，新仓库接入不依赖本人。我承认关键架构决策目前仍集中在我这里——展望里的 AgentOPS 绩效看板（缺口 1）正是为了把'翁金林的判断'变成'体系的判断'。"

### Q8. 绩效落差（最敏感，务必按真实情况校准）

**答辩口径框架：**

"三点回应：

①**时间线**：2024 年考核的是 2024 年度贡献——主业绩 Harness 2026.04 才立项，2024 年我处在 QMS 转换器模块化重构与 MDM 视图引擎建设期（git 提交 89%/95.5% 为证），是执行层的高产出年，但承载项目不是当年度部门最优先事项。

### Q9. 错题本"同类"判定

**答辩口径：**

"当前是**半自动、人把门**的机制，设计原则是'AI 不能自说自话改知识库'：

- **判定**：四源采集（审查打回/测试踩坑/发布踩坑/人工测试复盘）→ 条目写成命令级 ❌/✅ 对照 → 采集时人工归类 + 关键词归并识别'同类' → **晋升动作必经人类确认**（人审 MR 入库）。第 2 次出现触发晋升建议，红线生效由人拍板。
- **窗口期控制**：条目入库前，该教训已在当次 MR/复盘中被消化；各角色**开工必读错题本、视同本级约束**——即窗口期内新起的会话也会第一时间检索到未晋升条目。窗口期长度 = 一次人审 MR 周期，不是'等踩第二次坑'。
- **诚实承认**：语义级自动匹配（本体化：对象+关系+规则+动作，可校验可推理）是我自己盘点的五个缺口之一（缺口 3），在下一步路线图上。"

### Q10. 跨团队落地

**答辩口径：**

"现状如实回答：目前 6 个系统全部在流程与信息技术部内，跨部门采用是零——'具备跨团队借鉴条件'指的是技术事实：治理骨架与脚手架是仓库无关的，按目标仓库技术栈实铺 standards/ 即可迁移。

下一步动作对齐报告五缺口路线图：①**业务线体试点**（报表/数据治理）作为跨域样板——让其他部门看到'线体'而非'开发工具'；②按端到端业务能力串联跨系统流水线（缺口 4）；③打包'可复制建区包 + 培训材料'（四代演进文档已备好）。时间点：以业务线体试点为第一步，目标在下一考核周期内落地第一个部门外样板。"
