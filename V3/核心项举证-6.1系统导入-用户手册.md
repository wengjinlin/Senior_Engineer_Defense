## 2 用途

### 2.1 功能

- **一键建区**：一句话触发，6 步自动串联完成新工作区全链建设（详见 §4.1）；
- **需求流水线**：接入后各业务需求按五阶段链由 AI 角色接力交付（详见《概要设计说明书》）；
- **运行维护**：旁路 autopilot 自动巡检、文档对账、测试复盘。

### 2.2 性能（性能瓶颈定位与调优，对应行为标准③四层逐层映射）

本项目为"AI 编码流水线平台"而非传统单一应用，性能调优按行为标准四层逐层映射定位——每层的瓶颈定位、调优措施与效果如下（所有措施均出自已落地实物，无 hypothetical 项）：

| 行为标准层面 | 本项目对应对象 | 瓶颈定位 | 调优措施 | 效果 |
|---|---|---|---|---|
| **操作系统**（Windows 代码页/区域设置层） | agent CLI 与批处理运行所在的 Windows 主机 | 中文参数经命令行传递时被 OS 默认代码页（GBK/936）二次编码，批处理偶发乱码失败——根因在 OS 区域设置层而非应用缺陷 | 定位：乱码字节对比定位到 GBK 编码层；调优：全链路强制 UTF-8 输出（Python `sys.stdout.reconfigure(encoding='utf-8')`）+ CLI 中文参数一律 `@文件` 传参（经 multica_call.py 读取 UTF-8 文件内容），绕开命令行编码转换 | 根治一类问题（定性结论：固化为全局铁律后同类乱码不再复现）；量化佐证：MR 凭证中 2026.04-11 共 14 个 MR 全部含中文 change 主题正常合入，无一因传参乱码失败 |
| **数据库**（业务库批处理与结构文档对账负载） | 目标业务库（Oracle）：批处理定时任务 + 结构文档流水线 | ① 4211 工厂扩建定时任务：分布式锁致 5 实例仅 1 个执行（4 个空闲）、万条物料一次性加载内存、单个大事务运行（详见下文调优实例）；② 全量 diff 扫描对账开销大、对库产生无谓负载 | ① 定时任务改造：SQL 分片（`MOD(nZhuid, shardTotal) = shardIndex`）+ Nacos 实例列表自动分配分片 + 移除分布式锁 + 线程池并发 + `TransactionTemplate` 每条物料独立事务；② 基线增量对账（仅 diff 基线以来变更，无差异静默）；库表导出单连接单次即弃 | ① 定量：实例利用率 1/5 → 5/5，单实例数据量降至 1/5，事务失败影响面从整批回滚降为单条重试，改动约 150 行零新依赖（proposal/design 原文数字）；② 定性结论：对账开销与库负载最小化 |
| **应用服务器**（Multica 服务调度层：Go 后端 + Runtime） | Mika 调度与 3 autopilot 定时任务 | 轮询调度延迟高、空耗资源；多定时任务同点触发撞车 | 事件驱动"编排信号"（完成评论秒级唤醒）替代轮询，cron 仅 30 分钟兜底；cron 错峰配置：巡检 */30min / 文档对账周一 08:17 / 测试复盘周一 08:23 | 定量：接力延迟从分钟级（轮询周期）降至秒级（事件唤醒）；定性结论：定时任务错峰零同点冲突 |
| **应用程序**（模型调用/并发吞吐） | agent 工序与 Developer 编码实例 | 全工序用大模型 token 成本高；单开发实例串行吞吐低 | 模型分级路由（骨架 config `model_routing_hints`：explore 用 haiku / propose·review 用 opus / apply 用 sonnet）；Developer 5 实例并行 + 排他文件清单防写冲突 | 定性结论：同质量基线下单位需求 token 成本下压、单需求吞吐提升（路由配置实物 `files/治理骨架模板/openspec-config.yaml`；并行度 5 为实测稳定上限，见 4.3 举证 §3.6(b) 参数分析） |

> 映射说明：本项目无传统意义的"单应用 JVM/连接池"调优对象——其"应用服务器"职能由 Multica 调度层承担、"数据库"职能对象为业务库批处理与结构文档流水线，上表按实际对象逐层对应行为标准③的枚举层面；效果列凡无原始计时/计费记录者均标注"定性结论"。

**定时任务批处理调优实例（数据库层 + 应用程序层实证，2026.04）**——MDM 仓库 4211 工厂自动扩建定时任务（change `2026-04-09-task-2026030925`，proposal + design 全文归档 `files/实战记录/MDM-04月实战产出/`）：

| 维度 | 改造前 | 改造后（方案 B：SQL 分片 + 线程池） |
|---|---|---|
| 实例利用 | 分布式锁 `factory-4211-extension-lock`，5 实例仅 1 个执行、4 个空闲 | `MOD(nZhuid, shardTotal) = shardIndex` 分片，5 实例全部并行，锁完全移除（幂等校验兜底） |
| 数据加载 | 查询 SQL 一次性加载全部待扩建物料（万条级） | 每实例只查自己分片，单实例数据量降至 1/5 |
| 事务粒度 | 整个批处理在单个 `@Transactional` 大事务 | `TransactionTemplate` 编程式事务，每条物料独立事务，单条失败不影响其他 |
| 实例内并发 | 串行逐条处理 | 固定大小线程池（poolSize 默认 2，配置可调），`CountDownLatch` 等待收口 |
| 依赖与改动 | 此前 Kafka 方案（方案 A）引入较重外部依赖 | 零新依赖，改动约 150 行（Nacos `DiscoveryClient` 自动分配分片，扩缩容自动适应） |

该 change 于 2026-04-10 合入 master（MR 时间戳凭证在案）；分片参数获取、线程池配置、事务管理共 7 项技术决策及备选方案比选见归档 design.md。

### 2.3 安全保密（系统性预案，对应行为标准①）

- **密钥安全预案**：环境变量全部走人工网页注入通道，agent 只能在自己进程内读取、永不落盘到文档/评论/脚本参数；数据库密码两路策略（配置内密码确认后登记位置指针 / 用户提供单次 env 用完即弃）；
- **失败自愈预案**：30 分钟级兜底巡检自动重路由失败任务；连续失败 ≥2 次停止重试并升级人工，防止错误放大；
- **回退安全预案**：所有变更走 `feature/{change-id}` → MR 人工合并；部署配置列入保护路径，物理上防误改；
- **幂等与断点续传预案**：一键建区每步可重入，中断后单条指令恢复，无脏状态。

## 4 使用过程

### 4.1 安装与初始化（一键建区六步链，导入方案编写，对应行为标准①）

对 Mika 说「安装工作区」即触发，chat 内单会话执行（幂等 · 断点续传）：

```
① aicoding-workspace-setup   主入口，幂等探测断点续传（中断后说「继续安装」）
② aicoding-skills-bootstrap  zip 通道拉技能（整包入库防附带文档丢失）
③ aicoding-agent-bootstrap   按 agents/*.md 批量建 7 角色
   → 人工窗口①：GitLab 连接 + webhook + env 注入（网页操作）
④ aicoding-project-init      建项目 · 绑仓库 · checkout 验证
⑤ aicoding-orchestration-bootstrap  铺 Mika 接力 + 3 autopilot
⑥ aicoding-harness-bootstrap 铺仓库骨架（5 步）→ feature/init-harness → MR
   → 人工窗口②：人审合并 harness MR + 审宪法首版
```

> 人工参与口径：启动前**一轮问答**（确认系统范围与仓库信息）+ 上述 **2 个人工窗口**——与六步链图一致（bootstrap/aicoding-workspace-setup/SKILL.md 原文："人工仅开头一轮问答 + 一次网页操作窗口，结尾人审 harness MR"）。

**目标仓库治理铺设 5 步**：①前置（checkout/建分支/已有文档对齐模式/数据库预检两路校验）→ ②铺 skeleton（20+ 文件原样拷入）→ ③代码分析填充（16 项占位符逐条消灭，**每条须有代码证据**）→ ④hook 自测 → ⑤交付（**占位未清不得 commit**，人审 MR）。

**hook 自测标准**（部署完成的验收判据）：写保护路径应被 block、普通路径应放行——**自测不过不算装好**。

**部署方案可行性评估结论**（对应行为标准①）：

| 评估项 | 结论 |
|---|---|
| 自托管 Multica 平台（Go + PostgreSQL + 本机 Runtime） | 私有化部署可行，数据不出公司，满足信息安全 |
| agent 运行时（Claude Code 等 CLI） | 本机 Runtime 守护进程拉起，无需中心化算力池 |
| 与公司 GitLab / 数据库集成 | webhook + 环境变量通道打通，对现有系统零侵入 |

### 4.2 输入

- **输入数据的现实背景**：一句自然语言需求或「安装工作区」指令；
- **输入格式**：chat 自然语言；人工门输入（G1 审四工件+执行两份 SQL 并回帖验证 SELECT 输出；G2 审 MR）；
- **输入举例**：「给 MDM 加一个物料工厂变体视图维护的 PLM 继承接口」→ PM 澄清建单走五阶段链。

### 4.3 输出

- **输出数据的现实背景**：全周期交付工件与可审计记录；
- **输出格式**：四工件（proposal/specs/design/api）、ddl.sql 与 auth-resource.sql（人工执行）、代码+测试、review-report、test-report、MR（description 含 Closes {issue}）、QA 报告、结构文档增量 MR、对账基线表；
- **输出举例**：MDM 实战输出——新增 7 文件、修改 6 个 Mapper（10 方法+9 段 XML）、Tests run: 22, Failures: 0（`files/实战记录/MDM-PLM继承接口/6.md`）；Multica 阶段输出——商品码清洗 10 文件 +431 行四工件同 MR（`files/实战记录/MDM-商品码清洗-Multica阶段/`）。

### 4.4 文卷查询

issue 看板（过程可视 + agent 边做边评论留痕）；docs/ 目录（知识字典与错题本按角色分文件）；docs/index.md「结构文档同步状态」节的对账基线 commit（系统运行状态自动台账，人不填）。

### 4.5 出错处理和恢复（部署指导与问题解决，对应行为标准②）

- 编制**人工窗口操作指引**（GitLab 连接、webhook 配置、环境变量注入、MR 审核操作）；
- 设计**数据库连接预检**（双通道密码校验），部署前暴露连接问题而非运行中；连不上时支持人工在能连库机器跑脚本回传 `schema_dump.json`，**不得产出空的 database 文档**；
- run 失败断点重路由 / 连败 ≥2 升级人工 / 打回红色退回 / 信号丢失 30min 兜底；
- 六个业务系统接入期间的部署方案答疑与问题解决由本人支撑（六个仓库均已完成接入，MR 合并时间戳见 `files/凭证/MR时间戳凭证-GitLab合并记录.md`，其中 MDM 仓库 2026.04-11 共 14 个 MR 记录接入后持续交付节奏；其余系统接入 MR 由各团队侧操作合并，聊天/工单记录未随案归档）。

**写入拦截钩子实物**（guard_write.py，部署于每个目标仓库 `.claude/hooks/`；以下摘录自**骨架模板版** `files/治理骨架模板/hooks/guard_write.py`，66 行）：

```python
PROTECTED_PATTERNS = [
    re.compile(r"application(-[\w-]+)?\.yml$", re.IGNORECASE),
    re.compile(r"docs/db/", re.IGNORECASE),
    re.compile(r"(^|/)db/", re.IGNORECASE),
    re.compile(r"(^|/)sql/", re.IGNORECASE),
    re.compile(r"settings\.xml$", re.IGNORECASE),
    re.compile(r"pom\.xml$", re.IGNORECASE),
]
BLOCK_REASON_TEMPLATE = (
    "保护目录禁止写入：{path}\n"
    "如需变更，请在 openspec/changes/{change}/design.md 中显式声明，"
    "并经 Reviewer 审核通过后再由 hook 临时放行。"
)
# 机制：stdin 读 tool_input.file_path → 命中模式输出 {"decision": "block"} → 拦截生效
```

> 两版说明与逃生阀交代：QMS 早期实铺版（`files/治理文件实物/hooks/guard_write.py`，149 行变体）拦截清单不含 settings.xml/pom.xml，采用 exit(2) 机制，并设 **HARNESS_ALLOW_WRITE=1 受控逃生阀**——仅编排器受控流程（design 已声明、Reviewer 已过的临时放行）可设置，日常 agent 会话不注入该变量；骨架模板版对 stdin 解析异常采取保守放行（exit 0 静默）但异常路径有日志可查。拦截口径如实表述为"默认拦截 + 编排器受控通道 + 异常保守放行可审计，日常运行零违反"，而非绝对化的"物理不可绕过"。

**典型部署问题解决案例**（根治一类问题而非个案）：Windows 环境中文参数 GBK 代码页乱码导致批处理失败——定位到 OS 代码页根因后固化为全局铁律（CLI 中文参数一律 `@文件` 传参，经 multica_call.py 读取 UTF-8 文件内容传参）写入规范，全部脚手架统一适用（该案例的四层定位见 §2.2 操作系统层行）。

### 4.6 终端操作

日常操作收敛为：chat 一句话（建单/建区/澄清）、两个人工决策动作（G1/G2）、周级人审 MR（对账/复盘产出）。其余全部自动。

## 5 导入后的运行维护机制（持续保障）

**文档维护规则 5 条**（docs/index.md 实物摘录）：

> 1. **代码结构变更** → 对应文档在**同一个 change** 内更新：Tech-Lead 在 tasks.md 显式安排文档 task，不允许「事后补文档」
> 2. **数据库表结构变更** → DDL 人工执行后，按再生成规则重生成受影响域文档
> 3. **踩坑沉淀分流**：可复用平台用法进 help/；一次性踩坑进 lessons/；隐性约定进 implicit-contracts/；人工测试问题经复盘提炼进 lessons/
> 4. 本索引只在目录级变化时更新，不维护条目内容
> 5. **结构文档对账兜底**：DocKeeper agent（周级 autopilot）按 aicoding-harness-audit 对基线以来增量对账，自动项走 MR，DDL 与存疑项提醒人工

**对账基线表**：由 DocKeeper agent 自动维护，人不填——每次对账登记基线 commit，随 MR 前移，系统运行状态的自动台账。
